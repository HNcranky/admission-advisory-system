Chapter~\ref{chapter:Related_works} derived the system's functional and non-functional requirements.
This chapter selects the technologies that meet them.
Each section follows the same line of reasoning: what the requirement demands, which approaches could supply it, and why one was chosen over the alternatives, so that the design in Chapter~\ref{chapter:Experiment} rests on explicit decisions rather than convention.
Section~\ref{section:3.1} covers large language models and structured output, Section~\ref{section:3.2} retrieval-augmented generation over vector search, Section~\ref{section:3.3} the agentic pipeline, Section~\ref{section:3.4} document processing, Section~\ref{section:3.5} the web stack, and Section~\ref{section:3.6} observability and answer caching.

\section{Large language models and structured output}
\label{section:3.1}

The system needs natural-language reasoning at several points - intent classification, conflict tie-breaking, knowledge answering, and \gls{OCR} - without the budget to train a model for each.
A \gls{LLM} makes this feasible through two post-training properties.
\textit{Instruction tuning} fine-tunes a base model on instruction--response pairs so it follows natural-language directions~\cite{ouyang2022instruct}, and \textit{in-context learning} lets a sufficiently large model perform a new task from instructions and a few examples in its prompt, with no parameter update~\cite{brown2020fewshot}.
The underlying Transformer architecture lets every token attend to every other token~\cite{vaswani2017attention}, so a whole retrieved passage or a full profile can be reasoned over in one prompt.
Every \gls{LLM}-backed step in this system is therefore a prompt to a hosted instruction-tuned model rather than a trained component.

Three prompting techniques recur.

\begin{itemize}
    \item \textit{Role-and-instruction} prompting fixes the model's task through a system prompt and is used alone by intent routing.
    \item \textit{Few-shot} prompting adds worked exemplars where the output is easier to show than to specify.
    \item \textit{Chain-of-thought} prompting asks for intermediate reasoning before the answer~\cite{wei2022cot}, which helps the conflict tie-breaking and final-explanation steps, because both must justify a decision rather than only state it.
\end{itemize}
Decoding is left at the provider's defaults, except that a degenerate transcription is retried at a higher \textit{temperature} to break a repetition loop, a mechanism returned to in Section~\ref{section:3.4} and Section~\ref{section:5.2}.

A bare \gls{LLM} remains prone to \textit{hallucination}: fluent but unsupported statements never present in its input~\cite{ji2023hallucination}.
For an advisory system whose output must reflect official data this is the central risk, and two decisions in this chapter contain it: grounding the model on retrieved passages (Section~\ref{section:3.2}) and validating its output against an expected schema.
The system uses the Gemini family of hosted multimodal models~\cite{gemini, geminiteam2023}.
The multimodal capability is what lets the same interface serve both text reasoning and the \gls{OCR} of Section~\ref{section:3.4}.
A hosted model was preferred over a self-hosted open-weight one because the project's goal is engineering a reliable system around an external model, not training one.
The cost is a dependency on a quota-limited service that can fail at times, which directly motivates the graceful-degradation requirement NFR-01.

Where a step's result feeds downstream code, the prompt requests \textit{structured output} - strict \gls{JSON} parsed into a typed object.
Such a response can pass the network layer cleanly yet be unusable: prose around the \gls{JSON}, malformed syntax, or an out-of-range value.
The system therefore distinguishes a \textit{hard \gls{API} failure} (network, authentication, rate limit) from a \textit{structure failure} (a successful call whose body cannot be parsed), recorded as the \texttt{failure\_type} field on the gateway's result.
A \texttt{STRUCTURE\_FAILURE} is retried and then escalated to a fallback model, whereas a hard failure stops retrying immediately; the full policy is treated as a contribution in Section~\ref{section:5.1}.

\section{Retrieval-augmented generation and vector search}
\label{section:3.2}

A bare \gls{LLM} cannot answer questions about current admission documents: the information postdates or never entered its training data, and asking directly invites fabrication.
Retrieval-augmented generation (\gls{RAG}) retrieves relevant passages from an external corpus and conditions the answer on them~\cite{lewis2020rag}.
A survey frames \gls{RAG} as a design space rather than one recipe~\cite{gao2023ragsurvey}; this system adopts the simplest effective point in it - retrieve-then-read over a frozen retriever and generator - because the corpus is small and the goal is grounding, not retrieval training.
This serves UC-02: the knowledge step retrieves passages from ingested official documents, answers only from them with citations, and returns nothing when they are insufficient.

Retrieval uses \textit{semantic vector search} over \textit{embeddings}: dense vectors in which semantic similarity becomes geometric proximity~\cite{reimers2019sbert}, the basis of dense passage retrieval for question answering~\cite{karpukhin2020dpr}.
Each document is split into chunks, each chunk embedded, and the chunks nearest a question's embedding are returned.
The system embeds through Gemini's endpoint with asymmetric task types (\texttt{RETRIEVAL\_DOCUMENT} for chunks, \texttt{RETRIEVAL\_QUERY} for questions) and a fixed dimension of 768 to match the database schema.
Chunking cuts at blank-line block boundaries with a fixed overlap, trading off dilution (chunks too large) against fragmentation (chunks too small) by keeping each chunk a coherent unit of meaning.

Proximity is measured by \textit{cosine similarity}, $\cos(\mathbf{u},\mathbf{v}) = \frac{\mathbf{u}\cdot\mathbf{v}}{\lVert\mathbf{u}\rVert\,\lVert\mathbf{v}\rVert}$, with cosine distance $1-\cos(\mathbf{u},\mathbf{v})$.
This is exactly the retrieval \gls{SQL}: chunks are ordered by the pgvector operator \texttt{embedding <=> query} and scored as \texttt{1 - (embedding <=> query)}.
The vectors live in PostgreSQL~\cite{postgresql} via the pgvector extension~\cite{pgvector}, which adds a native \texttt{vector} type and an \gls{HNSW} index for approximate nearest-neighbor (\gls{ANN}) search in logarithmic expected time~\cite{malkov2020hnsw}.
At this scale an exact scan would suffice, but the index is cheap to maintain and keeps latency flat as the corpus grows.
The alternative, a dedicated vector database, offers richer indexing at very large scale, but it adds a second datastore to deploy and keep consistent with the relational data.
Integrating vectors into the one PostgreSQL instance keeps the knowledge corpus, the canonical records, and the chat state in a single transactional store, which the conflict-tolerance requirement NFR-02 relies on.

\section{Agentic pipelines}
\label{section:3.3}

The advisory consultation is not one \gls{LLM} call but a sequence of stages - profile completion, candidate retrieval, conflict checking, eligibility ranking, policy application, and explanation - and coordinating them is the role of an \textit{agentic pipeline}.
Such designs span a spectrum: at one end an autonomous tool-use loop where the model decides each next action, at the other a fixed workflow whose stage order is set in advance~\cite{wang2024agentsurvey}.
The concrete autonomous alternative is a \textit{ReAct}-style loop that interleaves reasoning with tool calls~\cite{yao2023react}; it is flexible but decides its control flow at run time, so two runs on the same input can diverge.
That non-determinism is a poor fit here: a consultation must be reproducible so a profile correction's effect is attributable (UC-04, NFR-02), and it must expose a fixed per-stage trace to operators.

The system uses LangGraph~\cite{langgraph, langgraph_docs}, which expresses an agent as an explicit state graph: nodes are functions reading and writing a shared typed state, and edges fix their order.
The advisory pipeline is a fixed linear graph over the six stages, threaded by one Pydantic state object (\texttt{AgentState}) that each stage fills in turn.
A fixed graph is chosen for three reasons that map onto Chapter~\ref{chapter:Related_works}:

\begin{itemize}
    \item \textit{determinism} - the same profile yields the same stage sequence, so a correction's effect is attributable (UC-04, NFR-02);
    \item \textit{traceability} - named static stages can each emit a span to the observability backend (Section~\ref{section:5.3});
    \item \textit{separation of concerns} - each stage is an independently testable single-responsibility function (NFR-05).
\end{itemize}

A fixed stage order could equally be written as a bare sequence of Python calls, so the framework earns its place only if it supplies something that sequence does not.
Three things do.
First, the graph carries one typed state object along its edges, so stages exchange data through a single validated structure rather than ad-hoc arguments threaded by hand.
Second, every node is wrapped by one decorator, so the per-stage observability of Section~\ref{section:5.3} is obtained uniformly rather than re-instrumented at each call site.
Third, the same state-graph abstraction is reused beyond this linear pipeline: the conversation turn is a second graph whose intent router needs conditional edges a straight sequence cannot express, and the knowledge flow is a reusable subgraph shared by three call sites (Section~\ref{section:5.4}).
The cost is reduced flexibility - the graph cannot improvise a new stage order - but the advisory task has a stable shape, so the system sits deliberately at the structured end of the spectrum.

\section{Document processing and the OCR model choice}
\label{section:3.4}

The ingestion pipeline must turn heterogeneous official sources - \gls{HTML} pages and \gls{PDF} proposals, some scanned - into parseable text.
Born-digital \gls{PDF}s yield their embedded text layer and table structure through pdfplumber~\cite{pdfplumber}, with PyMuPDF~\cite{pymupdf} rendering pages to images where needed.
Scanned pages have no text layer and require \textit{optical character recognition} (\gls{OCR}).
Rather than add and operate a dedicated recognition engine, the system performs \gls{OCR} as image-to-text transcription by a multimodal \gls{LLM}: the same model that reasons over text also reads a rendered page, so an image-only page is rasterized to PNG and sent to the inference gateway with a transcription prompt.
Extraction is hybrid and per page - a page with a usable text layer is read directly, and only image-only pages incur a transcription call - so cost stays proportional to the number of scanned pages.

The remaining decision is which multimodal model to use.
The requirement is modest: read mostly tabular Vietnamese admission pages accurately, at the lowest cost, without introducing a second model dependency.
Several hosted multimodal models satisfy the capability requirement; they differ mainly in cost and in whether they are already the system's inference backbone.
Table~\ref{table:ocr-models} compares the candidates on these criteria.
Because the system already routes every other reasoning step through the Gemini gateway, choosing a Gemini model for \gls{OCR} adds no new integration, and the lightweight \texttt{gemini-2.5-flash-lite} tier is the cheapest option that transcribes these pages adequately, so it is used for \gls{OCR} while the slightly stronger \texttt{gemini-2.5-flash} is reserved for structured extraction.
An external model of the GPT-4o or Claude class would meet the capability requirement but at a higher cost tier and a second provider integration, with no accuracy gain that the admission-page workload requires.

Model-based \gls{OCR} brings a failure mode of its own: on pages with merged table cells the model can fall into a repetition loop and emit one character indefinitely.
The system detects this \textit{degenerate output} and retries at a higher temperature, a safeguard examined in detail as a contribution in Section~\ref{section:5.2}.

\section{Web stack}
\label{section:3.5}

The user-facing layer must acknowledge a student message immediately and run the advisory pipeline without blocking the request (NFR-04).
It is built on FastAPI~\cite{fastapi}, an \gls{ASGI} framework served by Uvicorn~\cite{uvicorn}, whose asynchronous model lets one worker keep many slow, \gls{API}-bound consultations in flight; the chat interface is rendered with Jinja2~\cite{jinja2} and updated by client-side polling.
Because a full run issues several \gls{LLM} calls and can take tens of seconds, it cannot execute inside the triggering request.
The endpoint instead writes a \texttt{queued} run record and returns at once, and a background worker claims the next run with \texttt{SELECT \dots\ FOR UPDATE SKIP LOCKED}, executes the pipeline, and writes the result back for the interface to poll.
A database-backed queue is preferred over a broker-backed task queue because the workload is a few long tasks, not thousands of concurrent ones, and a persisted run survives a restart rather than dying with an in-memory pool; a separate message broker would add operational components disproportionate to that scale (NFR-04).
Every boundary in the application is a Pydantic~\cite{pydantic} typed model, giving the inference requests, the agent state, and the chat schemas a validated contract.

\section{Observability and answer caching}
\label{section:3.6}

A multi-stage \gls{LLM} application is hard to debug from logs: one consultation fans out into six stages and several model calls, each with its own prompt, tokens, latency, and retry behavior.
\textit{\gls{LLM} observability} captures this as a structured \textit{trace} - a tree of \textit{spans}, with model calls recorded as \textit{generation} observations carrying prompt, output, and token counts~\cite{langfuse} - following the span-tree convention of distributed tracing~\cite{opentelemetry}.
Because the advisory graph is fixed, its trace tree has the same shape on every run, so a slow stage or a malformed response can be located precisely.
An earlier iteration captured stage events in its own table and an in-app panel, which showed stage timings but no prompt, token, or retry detail; the system therefore adopts Langfuse as a single self-hosted trace sink, rejecting the custom panel as a higher-maintenance duplicate of an existing tool, and keeping captured prompts and student messages on the same machine (NFR-03).
The realization is presented as a contribution in Section~\ref{section:5.3}.

A second concern is the cost and latency of repeated calls.
Because many students ask near-identical factual questions, a \textit{semantic cache} can reuse a previous answer when a new question is close enough in embedding space, generalizing an exact-match cache by accepting a stored answer within a similarity threshold~\cite{bang2023gptcache}.
The risk is staleness - a cached answer can outlive the document it summarizes - so the cache is invalidated when the corpus changes; the version-gated design is detailed in Section~\ref{section:5.5}.

This chapter selected the system's technologies against its requirements, and in each case named the alternative that was rejected.
Hallucination is contained with instruction-tuned hosted multimodal \gls{LLM}s and validated structured output, rather than a self-hosted or unconstrained model.
Grounded answering uses \gls{RAG} over pgvector's \gls{HNSW} index, rather than a separate vector database.
The advisory pipeline is a fixed LangGraph graph for deterministic and traceable advising, rather than a run-time ReAct loop.
Ingestion uses a hybrid text-and-\gls{OCR} extractor on the cheapest sufficient Gemini tier already in the gateway, rather than a second model provider.
The web layer is an asynchronous FastAPI stack with a durable database-backed run queue, rather than a broker-backed task queue.
Finally, observability is self-hosted and paired with a version-gated semantic cache, rather than a custom trace panel or no caching.
Chapter~\ref{chapter:Experiment} applies these technologies, presenting the system's design, implementation, and evaluation.
